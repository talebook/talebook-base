Architecture Note · Talebook Base

把 Calibre
拆到不需要 Qt

talebook-base 的无 Qt 运行时不是重新实现 Calibre，也不是让上游所有代码都摆脱 Qt；它用多阶段构建、白名单抽取、依赖替换和强制校验，保留 Talebook 真正需要的转换与书库能力。

BRANCH · only-ebook-convert SNAPSHOT · 3d49cd7186 + CURRENT WORKTREE UPDATED · 2026-07-15 FORMAT · SELF-CONTAINED HTML

TL;DR

完整 Calibre 与 Qt 只作为构建原料出现。构建器从 Debian Calibre 中挑出 CLI 转换、数据库、资源和少量原生插件，覆盖无 Qt 的适配代码，递归收集真正需要的 ELF 动态库，再把这棵私有运行时复制进干净的最终镜像。PDF 生成改走 WeasyPrint，图像处理改走 Pillow，PDF 输入使用 Poppler；Qt 文件、Qt 动态链接和运行时 Qt 导入则分别在构建与测试阶段被拒绝。

01核心原理：抽取，不是魔改整套 Calibre

理解这套方案最重要的前提，是把“上游源码树”“构建阶段安装包”和“最终运行时”看成三个不同对象。

最终镜像里没有 Qt，不代表构建过程中从未使用 Qt；它代表所有 Qt 依赖都被隔离在已经丢弃的构建阶段。

上游 Calibre 是桌面应用、电子书转换引擎、书库数据库、设备驱动、内容服务器和大量插件的集合。桌面与部分渲染路径深度依赖 PyQt/Qt，但 EPUB、MOBI、AZW3、DOCX、TXT 等格式的解析、OEB 中间表示、书库数据库与许多文本处理逻辑本身是 Python/C/C++ 能力，并非天然要求 Qt。

talebook-base 利用这个内部边界：只保留可在 CLI 场景下闭合的能力集合，对仍然穿过 Qt 边界的少数调用点做替换或封口。结果是一套面向 Talebook 服务端场景的 Calibre 子集，而不是“无 Qt 的完整 Calibre”。

02构建期有 Qt，运行期为什么能没有

Dockerfile.base 的第一阶段基于 debian:13-slim，通过 apt 安装完整 calibre、weasyprint 与 poppler-utils。这一步接受 Debian 包已经解决好的 Python 与原生库关系，把它们当成可靠的“零件仓库”。

随后 packaging/build-runtime-from-debian.sh 调用组合构建器，输出唯一一棵共享运行时。第二阶段重新从 python:3.13-slim-trixie 开始，只复制这棵目录；Docker 不会把前一阶段未被复制的 apt 包和文件层带进最终镜像。

BUILD-TIME

用完整包解决“从哪里取”

借 Debian Calibre 提供稳定的模块、资源、原生插件和依赖定位，不在镜像构建中重新编译整套 Calibre。

RUN-TIME

用最小闭包解决“真正带什么”

最终只包含命令可达的代码、白名单插件、资源、辅助程序及其动态库闭包。

容易误解的地方

“最终镜像没有 Qt”与“构建镜像完全不下载 Qt”是两件事。当前方案优化的是发布面的体积、攻击面和运行时耦合；构建阶段仍会临时下载完整 Calibre 依赖。

# Dockerfile.base 的关键边界（概念化）
FROM debian:13-slim AS runtime-build
RUN apt-get install calibre weasyprint poppler-utils
RUN build-runtime-from-debian.sh /usr/lib/talebook-calibre-runtime

FROM python:3.13-slim-trixie AS base
# 只跨阶段复制经过验证的结果
COPY --from=runtime-build /usr/lib/talebook-calibre-runtime/ \
  /usr/lib/talebook-calibre-runtime/

03能力切片：从“默认全量”改成“显式允许”

减依赖的关键不是逐个追着 Qt import 修补，而是先收窄产品承诺：只有白名单里的格式、插件与功能才进入运行时。

维度保留明确移除 / 拒绝
输入格式AZW、AZW3、DOCX、EPUB、MOBI、original_epub、PDF、PRC、TXT、ZIP开放目录、recipe 与未列入白名单的格式
轻量输出AZW3、EPUB、MOBI、PDF、TXT其余 Calibre 输出插件
Calibre 子系统转换核心、元数据、OEB、书库数据库、必要资源AI、devices、GUI、headless、scraper、server、web
Python 包Pillow、lxml、BeautifulSoup、CSS/HTML 解析等白名单PyQt6、qt、ImageQt、pip、无关依赖
原生插件ICU、freetype、podofo、speedup、SQLite 扩展等 14 个白名单插件未显式列出的 Calibre 原生插件
辅助程序pdftohtml、pdfinfo、pdftoppm、pdftotextGUI 程序与无关命令

src/calibre/customize/standalone_builtins.py 不再加载 Calibre 的全量内建插件注册表，而是显式构造输入、输出和元数据插件列表。这样做同时解决两个问题：功能范围变得可审计；被移除插件的模块也不会因为自动发现而偷偷拉回 Qt。

calibredb 是单独保留的能力。最终镜像安装系统的 python3-apsw 与 python3-xxhash，再把模块复制进私有 Python 运行时，使 Calibre 的数据库 CLI 和 Talebook 书库访问仍能工作，而不必带上桌面 GUI。

04五层去 Qt 防线

单纯删除 PyQt6 目录并不可靠：代码可能仍然导入 Qt，某个 .so 也可能通过 DT_NEEDED 动态链接 libQt6*。本项目把“无 Qt”做成五层相互独立的约束。

4.1 文件系统层

构建脚本通过 CALIBRE_DROP_DIRS、SITE_PACKAGES_ALLOWLIST 和 PLUGIN_ALLOWLIST 形成正反两套筛选。最终验证还会再次遍历产物，拒绝名称为 qt、PyQt6、Qt*、libQt* 的文件，以及除最小兼容桩之外的 calibre/gui2。

4.2 Python 导入层

standalone_common.install_qt_import_guard() 向 sys.meta_path 插入 finder。当任何代码试图导入 qt、qt.*、PyQt6 或 PyQt6.* 时立即抛出 ImportError。这把潜伏的依赖变成测试阶段可见的硬错误。

4.3 兼容缝与替代实现

少量模块只是因为 Calibre 的公共初始化路径而引用 GUI 类型，不代表实际 CLI 功能需要 GUI。构建器为此提供极小的 calibre.gui2.must_use_qt() 桩和空 DevicePlugin 类型；真正需要图像操作的路径则通过 img_shim.py 切换到 Pillow 实现。两类处理不能混为一谈：前者是接口兼容，后者是能力替换。

4.4 ELF 动态链接层

Python 目录里看不到 Qt 并不等于原生扩展没有 Qt。构建器从 Python 解释器、辅助程序、Calibre 插件和 WeasyPrint 原生栈出发执行 ldd，递归复制共享库；随后 validate_no_qt_dependencies() 对每个 ELF 再扫描一次，任何 Qt soname 都会失败。

4.5 运行结果层

最终 smoke test 不只检查“文件不存在”，还实际创建 Calibre 书库、运行 calibredb list，把 EPUB 转为 MOBI、AZW3、PDF，把包含中文和 emoji 的 TXT 转为 PDF，并用私有运行时的 pdftotext 回读中文。这可以发现“删得很干净，但功能已经坏了”的假成功。

05命令与数据流：同一个入口，两条渲染链

/usr/bin/ebook-convert 保留用户熟悉的 CLI 形状，但真正执行前会按输出扩展名路由。PDF 与其他格式走不同后端，共享同一套裁剪后的 Calibre 输入能力。

为什么 PDF 要单独分流

上游 Calibre 的完整 PDF 输出依赖更重的排版与 QtWebEngine 路径。项目保留 Calibre 的输入插件，把电子书先规范化为 OEB；weasy_pdf_binary.py 再按 spine 合并 XHTML、修正相对资源 URL、加载 CSS 与 CJK 字体，最后交给 WeasyPrint 生成 PDF。这样保留了 Calibre 对多种输入格式的理解，同时避开浏览器式 Qt 渲染器。

为什么仍有一个轻量 PDF 插件

standalone_pdf_output.py 提供一个极小、无 Qt 的 PDF 输出插件，重点保证文字、CJK 字体、非 BMP 字符的 ToUnicode 映射和纯图片书籍的基本输出。但公共 ebook-convert 遇到 .pdf 时默认分流到 WeasyPrint，以获得更完整的 HTML/CSS 排版。前者是最小闭包能力，后者是产品默认路径。

06依赖替代矩阵

移除 Qt 的本质不是“删一个包”，而是逐项判断：这个 Qt 能力要删除、替换，还是只需提供兼容接口。

07私有运行时与兼容路径契约

裁剪结果安装在独立路径 /usr/lib/talebook-calibre-runtime，避免与系统 Python 或未来的 Debian Calibre 包混淆。三个公开入口只负责设置隔离环境，再用私有解释器启动实际程序。

/usr/lib/talebook-calibre-runtime/
├── bin/python3                 # 私有 Python 解释器
├── bin/pdftohtml              # Poppler 辅助程序
├── bin/pdfinfo
├── bin/pdftoppm
├── bin/pdftotext
├── lib/                        # 收集后的原生动态库
├── lib/python/site-packages/   # 裁剪后的 Calibre + 白名单依赖
├── resources/                  # 必要资源、模板、数据库 SQL、字体
├── ebook-convert               # 轻量转换执行器
└── ebook-convert-pdf           # WeasyPrint PDF 执行器

/usr/bin/ebook-convert          # 公共兼容入口 + 路由
/usr/bin/ebook-convert-pdf      # 直接 PDF 入口
/usr/bin/calibredb              # 数据库 CLI
/usr/lib/calibre -> private runtime/site-packages
/usr/share/calibre -> private runtime/resources

sitecustomize.py 在私有解释器启动时注入 Calibre 约定的资源、扩展和可执行文件位置；入口脚本再设置 PYTHONHOME、PYTHONPATH、LD_LIBRARY_PATH 与两个 standalone 标志。

CALIBRE_STANDALONE_CONVERTER=1
CALIBRE_STANDALONE_FORBID_QT=1
TALEBOOK_CALIBRE_PRIVATE_RUNTIME=/usr/lib/talebook-calibre-runtime
PYTHONHOME=/usr/lib/talebook-calibre-runtime
PYTHONPATH=/usr/lib/talebook-calibre-runtime/lib/python/site-packages
LD_LIBRARY_PATH=/usr/lib/talebook-calibre-runtime/lib
兼容而不污染

/usr/lib/calibre 和 /usr/share/calibre 仍然存在，但只是指向私有运行时的符号链接。这样既满足 Talebook 与 Calibre 代码的历史路径假设，又保持真正的文件所有权和升级边界集中在一个目录。

08测试与 CI：同时证明“没有”和“还能用”

无 Qt 运行时需要证明两个互补命题：Qt 确实没有进入产物；保留下来的功能确实能在最终镜像中工作。项目把验证分为四类。

  1. 构建产物检查：拒绝 Qt 命名文件、被禁止的 Calibre 目录、Pillow 的 ImageQt.py、断裂符号链接和非 root 所有者。
  2. 动态依赖检查：扫描所有 ELF 的 ldd 结果，拒绝 Qt* 与 libQt* soname。
  3. 运行时隔离检查：系统 Python 的 import PyQt6 必须失败；standalone 入口内部另有 import guard。
  4. 功能 smoke：验证三个公共命令、书库创建与列表、EPUB→MOBI/AZW3/PDF、直接 Weasy PDF、CJK 与 emoji 文本、PDF 中文回读。

GitHub Actions 工作流在 linux/amd64 和 linux/arm64 矩阵中构建镜像并运行同一份 packaging/smoke-test.sh。发布 job 依赖 test job，且只在手动触发并明确选择 push_image 时执行；普通 PR 和分支 push 只测试、不推送。

当前验证口径

仓库当前实现已经按上述 smoke 范围在本地 arm64 与交叉构建 amd64 镜像上通过。该结论针对当前工作树；后续修改白名单、Debian Calibre 版本或 PDF 后端时应重新运行完整镜像测试。

09边界、代价与维护风险

裁剪让运行时更小、更可控，但它把“兼容所有 Calibre 能力”换成了“稳定支持一组被测试过的服务端能力”。

SCOPE

不是全功能 Calibre

GUI、设备、server、scraper、recipe 和未列入白名单的格式不是遗漏，而是明确不支持。

FIDELITY

PDF 不是像素级等价

WeasyPrint 与 QtWebEngine 的 CSS、分页、字体回退行为不同，需要用代表性书籍做回归。

COMPATIBILITY

Debian 包版本是输入契约

构建器会对 Debian Calibre 文件做文本级补丁；上游结构变化时应让构建失败并重新审查，而非静默跳过。

BUILD COST

构建阶段仍然偏重

多阶段构建减少的是最终镜像，不会消除 apt 下载完整 Calibre 与 Qt 的构建时间和缓存占用。

维护原则

不要为了让某个新调用“先跑起来”而扩大复制整个 Calibre 子目录或放宽 Qt 校验。先判断它属于应删除、应替换还是应保留的产品能力，再最小化扩大白名单，并为新能力加入真实转换样本。

11如何在本地验证这套结论

最直接的验证不是在源码树里搜索 PyQt6——源码树本来就是完整 Calibre，而是检查最终镜像的文件、动态依赖与真实行为。

# 1. 构建最终镜像并运行完整 smoke
make test

# 2. 证明最终镜像的系统 Python 无法导入 PyQt6
docker run --rm talebook/talebook-base:slim-1.0 \
  python3 -c 'import PyQt6'   # 预期失败

# 3. 查看三个公开命令
docker run --rm talebook/talebook-base:slim-1.0 ebook-convert --version
docker run --rm talebook/talebook-base:slim-1.0 ebook-convert-pdf --help
docker run --rm talebook/talebook-base:slim-1.0 calibredb --version

# 4. 对私有 runtime 的 ELF 做额外审计（示意）
find /usr/lib/talebook-calibre-runtime -type f -exec file {} \; \
  | grep ELF

如果某次升级后构建在 patch_debian_*、validate_no_qt* 或 smoke test 处失败，这通常是有价值的信号：Debian Calibre 的代码边界或动态依赖发生了变化，需要重新审查，而不是绕过断言。

12结论

talebook-base 能移除 Qt，靠的不是一个神奇 patch，而是一组互相咬合的工程决策：缩小承诺面、从完整发行包抽取最小运行闭包、替换不可避免的渲染能力、隔离私有运行时，并用文件、导入、ELF 和端到端转换共同守住边界。

这套设计最值得复用的经验是：面对一个“看起来处处依赖 GUI 框架”的大型应用，不必从源码层追求全局纯化。先找到服务端真正需要的纵向能力切片，把自动发现改成白名单，把重依赖从可达路径上移走，再让构建系统证明最终产物只含预期闭包。
