Architecture Note · Talebook Base

把 Calibre
拆到不需要 Qt

talebook-base 的无 Qt 运行时不是重新实现 Calibre，也不是让上游所有代码都摆脱 Qt；它用多阶段构建、白名单抽取、依赖替换和强制校验，保留 Talebook 真正需要的转换与书库能力。

TL;DR

原始诉求：生成一份 HTML 文档，解释 talebook-base 的工作原理、如何从 Calibre 运行时移除 Qt 等依赖，以及具体修改文件；随后按 10xdev 规范迁移到 design/。

Calibre 与 Qt 的 Debian 包只作为下载取材池出现。构建阶段不执行 Calibre/Qt 安装：它用 apt --download-only 获取依赖闭包，以 dpkg-deb -x 解包非 Qt 包，再挑出 CLI 转换、数据库、资源和少量原生插件。最终镜像直接使用 Debian 系统 Python，PDF 生成走 WeasyPrint，图像处理走 Pillow，PDF 输入使用 Poppler；私有解释器、Qt 文件、Qt 动态链接与运行时 Qt 导入均被拒绝。

01核心原理：抽取，不是魔改整套 Calibre

理解这套方案最重要的前提，是把“上游源码树”“构建阶段安装包”和“最终运行时”看成三个不同对象。

最终镜像里没有 Qt，不代表构建过程中从未使用 Qt；它代表所有 Qt 依赖都被隔离在已经丢弃的构建阶段。

上游 Calibre 是桌面应用、电子书转换引擎、书库数据库、设备驱动、内容服务器和大量插件的集合。桌面与部分渲染路径深度依赖 PyQt/Qt，但 EPUB、MOBI、AZW3、DOCX、TXT 等格式的解析、OEB 中间表示、书库数据库与许多文本处理逻辑本身是 Python/C/C++ 能力，并非天然要求 Qt。

talebook-base 利用这个内部边界：只保留可在 CLI 场景下闭合的能力集合，对仍然穿过 Qt 边界的少数调用点做替换或封口。结果是一套面向 Talebook 服务端场景的 Calibre 子集，而不是“无 Qt 的完整 Calibre”。

02构建期下载 Qt，运行期为什么能没有

Dockerfile.base 的第一阶段基于 debian:13-slim，通过 apt 的 --download-only 模式获取 calibre、weasyprint 与 poppler-utils 的依赖闭包。apt 会下载 Qt 依赖，但不会运行 dpkg 安装脚本；extract-debian-packages.sh 随后按包名跳过 Qt/PyQt，只解开其它 .deb。

packaging/build-system-runtime-from-debian.sh 再调用白名单与 ELF 闭包构建器，并把结果转换成最终系统路径。它以最终 Debian 系统层为参照，只删除文件内容完全相同的动态库副本。独立的 python-wheel-build 阶段用编译工具链生成 QuickJS wheel；最后一阶段复用只含运行依赖的 runtime-system，通过只读 BuildKit mount 安装 wheel，再叠加裁剪后的代码、资源、helper 与原生库。私有 Python、编译器、headers 和 wheel 中间文件都不会进入发布镜像。

BUILD-TIME

用 Debian 包解决“从哪里取”

借 Debian Calibre 提供稳定的模块、资源、原生插件和依赖定位；只下载和解包，不把完整 Calibre 安装进构建 root。

RUN-TIME

用最小闭包解决“真正带什么”

最终只包含命令可达的代码、白名单插件、资源、辅助程序及其动态库闭包。

容易误解的地方

“最终镜像没有 Qt”与“构建镜像完全不下载 Qt”是两件事。当前方案优化的是发布面的体积、攻击面和运行时耦合；构建阶段仍会临时下载完整 Calibre 依赖。

体积结果

本地 arm64 镜像从 740,220,119 bytes（约 706 MiB）降到 356,153,818 bytes（约 340 MiB），减少 51.9%；/usr 从 701 MiB 降到 346 MiB。主要收益来自移出约 345 MiB 的编译工具链，以及删除 45 份与系统层完全相同的动态库。

# Dockerfile.base 的关键边界（概念化）
FROM debian:13-slim AS deb-packages
RUN apt-get install --download-only calibre weasyprint poppler-utils
RUN extract-debian-packages /var/cache/apt/archives /opt/debian-root

FROM debian:13-slim AS runtime-build
COPY --from=deb-packages /opt/debian-root/ /
RUN build-system-runtime-from-debian.sh /opt/talebook-system-root /opt/final-system

FROM runtime-system AS python-wheel-build
RUN apt-get install build-essential python3-dev ... && pip wheel quickjs

FROM runtime-system AS base
COPY --from=runtime-build /opt/talebook-system-root/ /

03能力切片：从“默认全量”改成“显式允许”

减依赖的关键不是逐个追着 Qt import 修补，而是先收窄产品承诺：只有白名单里的格式、插件与功能才进入运行时。

维度保留明确移除 / 拒绝
输入格式AZW、AZW3、DOCX、EPUB、MOBI、original_epub、PDF、PRC、TXT、ZIP开放目录、recipe 与未列入白名单的格式
轻量输出AZW3、EPUB、MOBI、TXT；PDF 由公共入口分流到 WeasyPrintCalibre PDF 输出插件与其余输出插件

Python 包系统 Python/pip；Pillow、lxml、BeautifulSoup、CSS/HTML 解析等白名单PyQt6、qt、ImageQt 与无关依赖
原生插件ICU、freetype、podofo、speedup、SQLite 扩展等 14 个白名单插件未显式列出的 Calibre 原生插件
辅助程序pdftohtml、pdfinfo、pdftoppm、pdftotextGUI 程序与无关命令

src/calibre/customize/standalone_builtins.py 不再加载 Calibre 的全量内建插件注册表，而是显式构造输入、输出和元数据插件列表。这样做同时解决两个问题：功能范围变得可审计；被移除插件的模块也不会因为自动发现而偷偷拉回 Qt。

calibredb 是单独保留的能力。最终镜像直接安装系统的 python3-apsw 与 python3-xxhash，由同一个 Debian Python 解释器加载 Calibre 代码和数据库扩展，使 Talebook 书库访问仍能工作，而不必带上桌面 GUI。

04五层去 Qt 防线

单纯删除 PyQt6 目录并不可靠：代码可能仍然导入 Qt，某个 .so 也可能通过 DT_NEEDED 动态链接 libQt6*。本项目把“无 Qt”做成五层相互独立的约束。

4.1 文件系统层

构建脚本通过 CALIBRE_DROP_DIRS、SITE_PACKAGES_ALLOWLIST 和 PLUGIN_ALLOWLIST 形成正反两套筛选。最终验证还会再次遍历产物，拒绝名称为 qt、PyQt6、Qt*、libQt* 的文件，以及除最小兼容桩之外的 calibre/gui2。

4.2 Python 导入层

standalone_common.install_qt_import_guard() 向 sys.meta_path 插入 finder。当任何代码试图导入 qt、qt.*、PyQt6 或 PyQt6.* 时立即抛出 ImportError。这把潜伏的依赖变成测试阶段可见的硬错误。

4.3 兼容缝与替代实现

少量模块只是因为 Calibre 的公共初始化路径而引用 GUI 类型，不代表实际 CLI 功能需要 GUI。构建器为此提供极小的 calibre.gui2.must_use_qt() 桩和空 DevicePlugin 类型；真正需要图像操作的路径则通过 img_shim.py 切换到 Pillow 实现。两类处理不能混为一谈：前者是接口兼容，后者是能力替换。

4.4 ELF 动态链接层

Python 目录里看不到 Qt 并不等于原生扩展没有 Qt。构建器从 Python 解释器、辅助程序、Calibre 插件和 WeasyPrint 原生栈出发执行 ldd，递归复制共享库；随后 validate_no_qt_dependencies() 对每个 ELF 再扫描一次，任何 Qt soname 都会失败。

4.5 运行结果层

最终 smoke test 不只检查“文件不存在”，还实际创建 Calibre 书库、运行 calibredb list，把 EPUB 转为 MOBI、AZW3、PDF，把包含中文和 emoji 的 TXT 转为 PDF，并用裁剪到 /usr/lib/talebook-calibre/bin 的 pdftotext 回读中文。这可以发现“删得很干净，但功能已经坏了”的假成功。

05命令与数据流：同一个入口，两条渲染链

/usr/bin/ebook-convert 保留用户熟悉的 CLI 形状，但真正执行前会按输出扩展名路由。PDF 与其他格式走不同后端，共享同一套裁剪后的 Calibre 输入能力。

为什么 PDF 要单独分流

上游 Calibre 的完整 PDF 输出依赖更重的排版与 QtWebEngine 路径。项目保留 Calibre 的输入插件，把电子书先规范化为 OEB；weasy_pdf_binary.py 再按 spine 合并 XHTML、修正相对资源 URL、加载 CSS 与 CJK 字体，最后交给 WeasyPrint 生成 PDF。这样保留了 Calibre 对多种输入格式的理解，同时避开浏览器式 Qt 渲染器。

为什么删除轻量 PDF 插件

上层 Talebook 没有调用 standalone_pdf_output.py，公共 ebook-convert 也始终把 .pdf 交给 WeasyPrint。继续保留第二套 PDF 输出只会扩大插件面、代码量和测试歧义，因此它已从源码覆盖、插件注册、轻量格式集合与样本矩阵中一并删除。

移除 Qt 的本质不是“删一个包”，而是逐项判断：这个 Qt 能力要删除、替换，还是只需提供兼容接口。

07系统 Python 与运行时路径契约

三个公开入口统一调用 /usr/bin/python3，不设置 PYTHONHOME，也不存在 /usr/lib/talebook-calibre-runtime。Calibre 与裁剪后的原生依赖使用明确的系统路径，避免复制 Python 标准库，同时保留 Talebook 依赖的历史 Calibre 路径。

/usr/bin/python3                     # Debian 系统解释器
/usr/bin/ebook-convert              # 公共兼容入口 + 路由
/usr/bin/ebook-convert-pdf          # 直接 PDF 入口
/usr/bin/calibredb                  # 数据库 CLI
/usr/lib/calibre/                   # Calibre + 白名单 Python 包
/usr/share/calibre/                 # 资源、模板、数据库 SQL、字体
/usr/lib/talebook-calibre/bin/      # Poppler helpers
├── pdftohtml
├── pdfinfo
├── pdftoppm
└── pdftotext
/usr/lib/talebook-calibre/lib/      # 收集后的非 Qt 动态库
/etc/talebook-calibre/fonts/        # Fontconfig 配置

入口脚本只设置代码、资源、helper 和原生库搜索路径，以及两个 standalone 安全标志。系统 pip 由 Debian 安装，并通过旧 Talebook 已使用的 PIP_BREAK_SYSTEM_PACKAGES=1 保持 pip install -r 能力。

CALIBRE_STANDALONE_CONVERTER=1
CALIBRE_STANDALONE_FORBID_QT=1
PYTHONPATH=/usr/lib/calibre
LD_LIBRARY_PATH=/usr/lib/talebook-calibre/lib
PATH=/usr/lib/talebook-calibre/bin:$PATH
PIP_BREAK_SYSTEM_PACKAGES=1
兼容而不污染

/usr/lib/calibre 和 /usr/share/calibre 现在是真实目录，不是指向私有运行时的符号链接。Calibre 的 Python 代码与系统 Python 解耦；解释器、标准库、pip、APSW 和 xxhash 由 Debian 统一管理，QuickJS 则由 builder 预编译后安装到同一个系统 Python。

08测试与 CI：同时证明“没有”和“还能用”

无 Qt 运行时需要证明两个互补命题：Qt 确实没有进入产物；保留下来的功能确实能在最终镜像中工作。项目把验证分为四类。

  1. 构建产物检查：拒绝 Qt 命名文件、被禁止的 Calibre 目录、Pillow 的 ImageQt.py、断裂符号链接和非 root 所有者。
  2. 动态依赖检查：扫描所有原生扩展与可执行文件的 ldd 结果，拒绝缺失依赖、Qt* 与 libQt* soname。
  3. 运行时隔离检查：系统 Python 的 import PyQt6 必须失败；standalone 入口内部另有 import guard；最终镜像不得安装 gcc 与开发工具链。
  4. 功能 smoke：验证三个公共命令、书库创建与列表、PNG/JPEG/GIF 图片矩阵、公共缩略图接口、数据库封面写入/读取、EPUB→MOBI/AZW3/PDF、直接 Weasy PDF、CJK 与 emoji 文本、PDF 中文回读。
  5. 体积门禁：/usr 不得超过 400 MiB，CI 同时打印各架构的 Docker image size 便于追踪。

GitHub Actions 工作流在 linux/amd64 和 linux/arm64 矩阵中构建镜像并运行同一份 packaging/smoke-test.sh。发布 job 依赖 test job，且只在手动触发并明确选择 push_image 时执行；普通 PR 和分支 push 只测试、不推送。

当前验证口径

优化后的系统 Python 方案已在本地 arm64 Docker 镜像完整通过上述 smoke，QuickJS 可由上层 pip install -r 直接复用，且 Fontconfig/CJK PDF 回读正常。Talebook 的 HTTP 缩略图定向测试已通过，完整 make test 结果为 575 passed、1 skipped。当前镜像约 340 MiB、/usr 为 346 MiB；CI 工作流继续负责独立验证 amd64 与 arm64。

09边界、代价与维护风险

裁剪让运行时更小、更可控，但它把“兼容所有 Calibre 能力”换成了“稳定支持一组被测试过的服务端能力”。

SCOPE

不是全功能 Calibre

GUI、设备、server、scraper、recipe 和未列入白名单的格式不是遗漏，而是明确不支持。

FIDELITY

PDF 不是像素级等价

WeasyPrint 与 QtWebEngine 的 CSS、分页、字体回退行为不同，需要用代表性书籍做回归。

COMPATIBILITY

Debian 包版本是输入契约

构建器会对 Debian Calibre 文件做文本级补丁；上游结构变化时应让构建失败并重新审查，而非静默跳过。

BUILD COST

构建阶段仍然偏重

多阶段构建减少的是最终镜像，不会消除 apt 下载完整 Calibre 与 Qt 的构建时间和缓存占用。

维护原则

不要为了让某个新调用“先跑起来”而扩大复制整个 Calibre 子目录或放宽 Qt 校验。先判断它属于应删除、应替换还是应保留的产品能力，再最小化扩大白名单，并为新能力加入真实转换样本。

11如何在本地验证这套结论

最直接的验证不是在源码树里搜索 PyQt6——源码树本来就是完整 Calibre，而是检查最终镜像的文件、动态依赖与真实行为。

# 1. 构建最终镜像并运行完整 smoke
make test

# 2. 证明最终镜像的系统 Python 无法导入 PyQt6
docker run --rm talebook/talebook-base:slim-1.0 \
  python3 -c 'import PyQt6'   # 预期失败

# 3. 查看三个公开命令
docker run --rm talebook/talebook-base:slim-1.0 ebook-convert --version
docker run --rm talebook/talebook-base:slim-1.0 ebook-convert-pdf --help
docker run --rm talebook/talebook-base:slim-1.0 calibredb --version

# 4. 对裁剪目录的 ELF 做额外审计（容器内示意）
find /usr/lib/calibre /usr/lib/talebook-calibre -type f -exec file {} \; \
  | grep ELF

如果某次升级后构建在 patch_debian_*、validate_no_qt* 或 smoke test 处失败，这通常是有价值的信号：Debian Calibre 的代码边界或动态依赖发生了变化，需要重新审查，而不是绕过断言。

12结论

talebook-base 能移除 Qt，靠的不是一个神奇 patch，而是一组互相咬合的工程决策：缩小承诺面、从 Debian 包抽取最小运行闭包、替换不可避免的渲染能力、复用系统 Python，并用文件、导入、ELF 和端到端转换共同守住边界。

这套设计最值得复用的经验是：面对一个“看起来处处依赖 GUI 框架”的大型应用，不必从源码层追求全局纯化。先找到服务端真正需要的纵向能力切片，把自动发现改成白名单，把重依赖从可达路径上移走，再让构建系统证明最终产物只含预期闭包。
